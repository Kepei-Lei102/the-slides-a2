P3

One student, two hundred thousand records

The city's student information system holds 200 000 records on disk. A school office asks for student 137452. How many records does the computer read before it can answer?
Every file you have ever processed — U7c's text files, every CSV, every log — you read from the front, one line at a time. If that is the only trick you have, the honest answer is: on average 100 000, and all 200 000 to be sure someone isn't there.
Today's whole topic is one question:
Who chose the order the records sit in?
Answer it three ways and you get the three file organisations — and the answer for one of them finds any record in one read.
P3

Who chose the order?

SERIAL — history chose
Records sit in the order they arrived — chronological, like a till roll or a sign-in sheet. Nobody decided; it just happened.
New record: stick it on the end. Free.
SEQUENTIAL — the key chose
Records sit in the order of a key field — a register sorted by student ID.
New record: it has a place, and putting it there costs — A2b's insertion problem, wearing a file extension.
RANDOM — nobody needs to choose
The position is computed from the key by a hashing algorithm. The records look scattered — hence "random" — but every one is exactly where its key says.
New record: compute, write. One step.
The published wording, Nov 2021 P31: in both serial and sequential files records are stored one after the other; serial files are stored in chronological order; sequential files are stored with ordered records, in the order of the key field; in serial files new records are appended; in sequential files new records are inserted in the correct position.
And the examiner checks this exact line. a recent sitting's marker guidance, on describing sequential organisation: "Chronological order is not correct — that would be serial organisation." Say key field for sequential, chronological / arrival order for serial, and the mark is safe.

A serial file, in real code

Not a diagram — the actual file operations. A visitors' log: three arrivals, then one more, then a search.

Adding took one line and touched nothing that was already there — append cannot corrupt the past, which is why logs are serial. Finding took four reads out of four records — and finding someone who never visited would take all of them, every time. That is the serial trade, executed rather than asserted.
P3

A sequential file — and what keeping order costs

The register is sorted by ID. Student 1300 joins. Watch what "inserted in the correct position" actually means for a file.

The insert copied the entire file to put one record in its place — a file cannot shuffle itself the way A2b's array could, so "insert in the correct position" means rewrite. The swap at the end is deliberate: the original is never half-written, so a crash mid-insert can never destroy the register. What did the pass buy? Finding can now stop early, and two sorted files merge in one pass — which is why payroll and billing run on sequential files.

📐 THE WORD DOES DOUBLE DUTY
"Sequential" names an organisation (records ordered by key field) and an access method (read one record after another). So "a serial file is read with sequential access" is a correct sentence in which the word means two different things. The confusion is in the vocabulary, not in you — and the fix is to always say which job the word is doing: sequential organisation or sequential access.
Read the table's second row again, because it hides the two best questions in the topic: how does direct access work on a sequential file (next slide), and on a random file (the slide after)? Different mechanisms — an index, and a hash — and June 2024 asked for both in one question.
P3

Direct access on a sequential file = an index

// the INDEX — a small file about the big one key 1043 → position 0 key 2049 → position 4 key 2661 → position 6 // find 2340: the index says "at or after // position 4" -- jump there, read 2 records, // done. 3 reads instead of 6.
The index only works because the big file is ordered — "at or after position 4" is only a meaningful promise when the keys run in order. This is why the examined sequential-file mechanism uses an additional index; order alone is not an address lookup.
The published answer, June 2024 P32: "In sequential files, an index of all key fields is kept. The index is searched for the address of the file location where the target record is stored."
And a marking trap, from a recent sitting's guidance: asked to outline plain sequential access, candidates who describe searching an index do not answer the question. The index is the answer to direct access on a sequential file — keep the two answers in separate pockets.
⬇ where every database keeps this idea
🕳 beyond the exam

Databases live right here

The index-on-a-sorted-file idea grew up and took over. IBM called it ISAM — Indexed Sequential Access Method — in the 1960s; its descendant, the B-tree, is an index of indexes of indexes, so even a billion-row table is "jump, jump, jump, read" — four or five reads, never a scan.
Every time a database answers a WHERE in milliseconds, this slide is what happened. And when it can't — no index on that column — it does exactly what the serial drawer does: reads every record. Database people call it a full table scan, and they say it the way doctors say "infection".
The trade never went away. An index makes reading fast and writing slower — every insert must update the index too, which is A2b's insertion cost moved one level up. Real systems choose which columns deserve an index the way you are choosing organisations today: by asking what will this file be asked to do most?
P3

Hashing — compute the address instead of finding it

The exam's hash is MOD — June 2023, published: hash = key modulus 3, so 1030 → 1, 1050 → 0, 1025 → 2. The remainder is the address. You have met MOD twice: the clock arithmetic of A2a's circular queue, and the ring buffer's index. Third job: the hash function.
Fixed-width records are what make it work. If every record is exactly REC bytes, then record N starts at byte N × REC — the array's address arithmetic, back from the dead. A random file is an array on disk, and the hash is how you know which element you want.

The exam's spelling — and you have already read it

November 2023 Paper 31 printed this and asked candidates what it does. It is the cell you just ran, in dialect.

OPENFILE AccountFile FOR RANDOM OUTPUT "Please enter an account number" INPUT Customer.AccountNumber Location ← Hash(Customer.AccountNumber) SEEK AccountFile, Location GETRECORD AccountFile, Customer OUTPUT Customer CLOSEFILE AccountFile
Three new keywords, one idea: FOR RANDOM opens for record-level jumping, SEEK moves the file pointer to a computed location, GETRECORD / PUTRECORD read and write the record sitting there. An address you computed is an address you can jump to — that is the entire random-file story. Writing these yourself is next lesson.
🕳 beyond the exam

How Python hashes — optional implementation detail

(Matches a fixed polynomial exactly for short strings; a fixed polynomial wraps the example uses arbitrary-precision Python integers; fixed-width algorithms may explicitly mask their result.)
The exam hashes numbers with MOD. Real languages hash anything — a string becomes a number by the polynomial on the left, and then… MOD again, down to a drawer. Two steps, same idea.
A dict / HashMap is this lesson's random file, living in RAM. Every d[key] you have ever written computed a hash, jumped to a slot, and handled the collisions you meet on the next slide. A2c called the dictionary an ADT and would not say how it works. Now you know.
And one true spy story: Python's own hash("...") gives a different answer every run — deliberately. In 2011, attackers realised that if you know the hash function you can send a web server thousands of keys that all collide, and its dictionaries grind to O(n). Python's fix: salt the hash at startup. A hash function so important it had to become unpredictable.

P3

Collisions — when two keys want one slot

1737 MOD 10 = 7. So does 2047. The second arrival finds the slot taken — a collision — and the file needs a rule. The exam gives you two, and the 4-mark question wants both.

Closed hash — probe onward. Search linearly from the home slot for the next available space and store the record there. You have met this: it is A2b's free-list instinct — "the next empty row" — walking forward one slot at a time.
Open hash — overflow area. A separate region at the end of the file; colliding records go there, and it is searched linearly when needed.
Retrieval retraces the same path. Compute the hash, look at the home slot — if the key there doesn't match, keep searching by the same rule (probe on, or scan the overflow area) until the key matches…
…or until you can stop: an empty slot (closed) or the end of the overflow area (open) means the search is over and the record is not in the file — the published mark scheme's own final bullet. Absence has a proof, and it is short.
One honest addition the mark scheme makes, Nov 2024: "a hashing algorithm is used in direct access methods on random and sequential files" — a hash can also feed a sequential file's index lookup. Don't let that MP surprise you: the syllabus's own bullet says hashing serves "a random / sequential file".
⬇ how the real world resolves them
🕳 beyond the exam

How the real world resolves collisions

The exam's two rules are real — but each is the ancestor of what your own dict and HashMap do. Same twelve keys as the drawers, same 16 slots, a third rule:

Slot 4 is the drawers' own cluster: with linear probing those four keys spilled into 5, 6, 7 and 8 — stealing slots from keys that hashed there honestly. Chaining keeps the mess inside the drawer that caused it.
1 · Chaining — every slot owns its own little list; a collision appends. That is the exam's open hash with an overflow area per slot instead of one shared one. Real hash tables choose a collision policy and a resizing/load-factor policy.
2 · Open addressing, but never in a straight line — Python's dict probes with i = (5·i + 1 + perturb) mod N, a scrambled walk that avoids the clusters linear probing breeds. And since 3.6 the dict keeps a small index array pointing into a dense entries array — the exam's index idea, inside the language.
3 · Don't fight load factor — grow. The exam's file has a fixed number of slots; a real table doubles itself when it passes a threshold (¾ full for HashMap, ⅔ for dict — that is what the byte jumps show) and re-inserts everything. Your load-factor curve tonight will climb to 4+ probes at 91 % full; resizing exists so a real program never gets there.
Further out: cuckoo hashing (two hash functions; a newcomer evicts the occupant to its other home, so a lookup is never more than two reads), and Swiss tables — Google's and Rust's default maps — which check 16 slots at once with one SIMD instruction. Different rules, one problem: two keys wanted one slot.
P3

🌍 Where each drawer runs the world

SERIAL — the log
The most-written file shape on earth. Every server log, every flight recorder, every journald — and Kafka, the pipe most of the internet's events flow through, is at heart an append-only serial file. Why: append is the one write that cannot corrupt what came before — a crash mid-append loses one record, never the file.
SEQUENTIAL — the batch
The mark scheme's own examples — payroll, billing, bank statements — are real: process every record once, in key order, merging sorted files as you go. And modern storage engines (LevelDB, RocksDB — inside your phone's apps) still write sorted runs and merge them: A2b's insight that sorted things merge cheaply, at industrial scale.
RANDOM — the hash
git files every object under its hash — the address is computed from the content, which is why git never searches for anything. Every database's hash index, every dict and HashMap, every cache: compute, jump, done.
Notice nobody "won". The world kept all three, because the trade never goes away: appending fast, reading in order, and jumping straight to a key are different superpowers, and every real system picks the one its workload needs — which is exactly the judgement §13.2 asks of you: select an appropriate method of file organisation for a given problem.

Check the mechanism

43: serial 3, sequential 4, hashed 1. Typical mistake: assuming key order itself supplies an index, or calling hashed placement chance.
Optional full reference
Serial appends 18, keeping arrival order. Sequential inserts 18 between 12 and 24, typically by rewriting/merging. Random: 18 MOD 5 = 3; slots 3 and 4 are occupied, so probe to empty slot 0. Retrieval hashes then follows the same probe path. An index is additional structure, required for the examined direct-access mechanism on a sequential file.

The sentences, in their words

Published mark schemes, quoted. These are the marks — learn the sentence, then let the code you ran today make it un-forgettable.

Who chose the order? History (serial — append free, search dear), the key field (sequential — insert dear, stop early and merge cheap), or a computation (random — one seek, mind the collisions).
