P3 + P4

You already built the node. Twice.

TYPE Node DECLARE Data : INTEGER DECLARE NextNode : INTEGER // the INDEX of the next node ENDTYPE

Named NextNode, never just Pointer — a node can carry more than one (a doubly-linked list has PreviousNode too), so the name must say which way it points. The June 2021 paper's own field is nextNode; the Nov 2024 table prints the column as bare Pointer. Read both as who comes next.

A record that contains a pointer. That is the entire new idea in this lesson, and you own both halves already — you declared the record and the pointer in the first lesson of the year.
A record holds things that belong together. A student's name and grade. A node's value — and the address of the next node.
So a list is not a container. Nothing "holds" the nodes. Each node knows exactly one thing about the outside world: who comes after me. The list exists only because they agree.

An array is a shelf. A linked list is an agreement.
Every node keeps one small promise — who comes next — and the list exists exactly as long as every promise holds.

📐 ONE REAL DIFFERENCE, NOT JUST A RENAME
In the class version nextNode holds another node. In the array version it holds a row number — and that is why the array needs −1 for "nobody" while the class can just say None/null. The sentinel exists because an index has no way to say nothing.
🧾 Both forms are examined. June 2021 Paper 41 declares a field called nextNode; Nov 2024 Paper 41 hands you the numbered array. Same structure, two costumes — and you will meet the first one again when a class stops being a record and starts owning its verbs.

P3 + P4

Insert at the front — and the order of the two writes

FirstNode = 3 — the index where the LIST starts FirstEmpty = 2 — the index where the SPARE nodes start
The list reads 12 → 7 → 25 → 4, so the new value is going to live at index 2 — that is the node the free list hands over.

// the new node is at index FirstEmpty LinkedList[FirstEmpty, 1] ← FirstNode FirstNode ← FirstEmpty
① point the new node at the old first.
② now make the new node the first.
Two writes. Nothing else in the array is touched, read, or moved.
And afterwards the new value sits at index 2 — the middle of the array. The front of the list is not the front of the array: nothing shuffles up to make room, because the order lives in the pointers, not in the positions.
Swap those two lines and the list is gone.
Move FirstNode first and the new node ends up pointing at itself — and the nodes that used to follow are still sitting in the array, perfectly intact, with nothing on earth pointing at them.
That is an orphan, and in a language that manages its own memory it has a second name: a leak. The data is not deleted. It is unreachable, which for a program is worse — it still occupies the space.

🕳 The bug that looks like it worked

A different slip, and the nastiest one in the topic: reading FirstEmpty's pointer after overwriting it.

The first insert is perfect. But FirstEmpty now points at a node that is in the list — so the second insert writes over live data, and the list eats itself. The mark scheme has a bullet for exactly this: read the next-empty index before any update to FirstEmpty's pointer.

P3 + P4

What you gave up to get it

THE ARRAY

Want the 500th item? A[499]. One calculation, O(1), no matter how big it is.
Want to insert at the front? Move everything.

THE LINKED LIST

Want the 500th item? Ask 500 nodes in turn. There is no index — O(n).
Want to insert at the front? Two writes.

So be careful with the hook. Inserting into the middle of a linked list still costs a walk to get there — both structures are O(n) for that. A linked list never saves you the search. It saves you the shuffle — and reading n pointers is a very different price from writing n records.
📐 AND ABOUT LAST LESSON'S PROMISE
The stack-and-queue deck closed with "next lesson: the one that does not have a size." Half true, and here is the honest half: this array is still fixed at 8 nodes, or 20, or 50 — when FirstEmpty reaches −1 you are full, exactly like the queue was. What actually changed is that the list's shape is now free while its storage is not. The version with no size at all needs the machine to hand you memory on demand — and that is what happens when the node stops being an array row and becomes an object.

Part (a) is worth two marks and most candidates lose one. Not for the array — for forgetting that an empty structure still has to be threaded: node 0 points at 1, node 1 at 2, and node 19 at −1. An "empty" linked list is not empty. It is a full list of nothing.

What you can build now

Traverse — start at FirstNode, hop until −1.
Insert — take a node from the free list, point it at the old first, move FirstNode.
Delete — re-point the predecessor, hand the node back.
And the idea underneath all three: one array, two lists, threaded through each other, and every operation is just changing who points at whom.
Every structure you have built is a line. Stack, queue, linked list — each node points at exactly one other node, so there is one way in and one way through. Which is why finding something still means asking everybody in turn.
