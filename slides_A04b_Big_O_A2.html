P3

Two things that are now false

✗ "a lower Big O is always faster"
Only eventually. Below the crossing the quadratic wins, and it wins by a factor of six at n = 10. Big O ranks scaling, not speed.
✗ "constants never matter"
They are dropped from the notation, not from the world. Below the crossing the constants decide everything.
And this is not a classroom curiosity. Hybrid sorting implementations can combine an O(n log n) strategy with insertion sorting on small runs. Their cutoffs depend on implementation and measurement; this widget is a cost model, not a benchmark.
The question is never "which algorithm is best?" It is "how big is n, really?"

Concept + exam scope

Space — what grows in memory?

9618 §19.1 includes time and space complexity. Here count extra (auxiliary) space, excluding the input array; one fixed-size value occupies constant space.

A · Scan and total
Read the n input values once. Keep only a running total and an index. Do not copy the array.
B · Copy and scan
Make a new array containing all n input values, then total them in one pass.

On paper: give the time and extra-space order of A and B. If n doubles, what happens to each memory requirement?

Check: both take O(n) time. Extra space: A O(1), B O(n). Counting the stored input as well gives O(n) total space for both.

Optional working

Space — full working

A: n reads and additions → O(n) time. A fixed number of counters and totals → O(1) extra space, unchanged when n doubles.
B: n copies + n additions → 2n work → O(n) time. n new slots plus fixed counters → O(n) extra space; doubling n doubles the dominant extra storage.
A real trade: a hash table uses O(n) storage to support expected O(1) lookup under suitable hashing and load. That is an expected-case claim; worst-case lookup can be O(n). State the model and case.

🕳 beyond the exam

Real-world extension — a B+ tree index

A common database index combines a balanced tree with linked leaves. Implementations vary.

Why not just a sorted array? Look at that row again: sorted array is O(log n) to find and O(n) to insert, because everything after the new row has to shuffle up. A database inserts all day. The array's find is perfect and its insert is fatal.
So the index is a tree — a B+ tree, a balanced search tree, with a fan-out in the hundreds rather than two. Ten million rows come out about three levels deep. Find and insert are both O(log n), and the balancing is not optional here, it is the product.
And its leaves are chained into a linked list — deliberately. That is what makes "every order between March and June" fast: find the first one down the tree, then walk sideways instead of searching again. Your linked list's O(1) once-you-are-there, bought on purpose.
Then the row itself is reached by a direct pointer to its page — much closer to A[i] than to following a chain.
Tree to find it · linked leaves to scan a range · a pointer to read it. All three rows of that table, inside one structure — because each one is the best answer to a different question.
🕳 beyond the exam

Why n log n? — the one that feels invented

O(n) is "look at each thing once". O(n²) is "everything against everything". But n log n is not a picture — until you count levels. 9618 assesses neither merge sort nor quicksort; this is here because it answers "is there anything better than my three sorts?"

Every level costs n — the pieces got smaller but there are proportionally more of them, so each row still covers all n items exactly once. And there are log₂ n levels, because that is how many halvings take n down to 1. n × log₂ n. That is the whole secret: one linear sweep at every level of a halving.
And it explains quicksort's disaster in one sentence. A good pivot halves the range — log n levels, so n log n. A bad pivot peels off one element at a time — n levels, so n × n. Same work per level; different number of levels.
🕳 One more, free: comparison sorting needs Ω(n log n) comparisons in the worst case. There are n! possible orderings and each comparison halves the possibilities, so you need at least log₂(n!) ≈ n log n of them. Merge sort does not just do well — it hits the floor.
🕳 beyond the exam

The wall — where no computer helps

An O(2ⁿ) algorithm on just n = 100 needs about 1.3 × 10³⁰ operations.
At a billion a second that is 4 × 10¹³ years — about three thousand times the age of the universe.
There is no hardware answer. There is only a better algorithm, or no answer.
You already rely on this. A password of length L from 26 letters has 26L possibilities. Adding one character multiplies the attacker's work by 26.
That is why length beats cleverness in a password — you are buying an exponent, not a constant.
🕳 And the line itself is the biggest open question in computer science. Think of a hard Sudoku: agony to fill in, trivial to check once somebody hands you a filled grid.
P — Polynomial time — the problems we can solve quickly.  ·  NP — Nondeterministic Polynomial time — the problems whose answers we can check quickly. NP does not mean "non-polynomial" — that is the single most common misreading of the name, and every P problem is also in NP.
Is finding really harder than checking? Nobody knows. Almost everyone believes it; nobody can prove it. There is a $1 000 000 prize for the answer, unclaimed since 2000.
 

What you can now say

The two values — linear O(n), binary O(log₂ n) — and the sentence that carries them: the time increases logarithmically as the items increase linearly.
Read an order off unseen code: sequential adds, nested multiplies, halving is a logarithm.
And the two honest edges — Big O is not "the worst case" until you say so, and a lower Big O is not faster until n is past the crossing.
Time and space: name the cost model, count what grows, and state the case. Measurements test a prediction; a finite ratio does not prove a bound.
