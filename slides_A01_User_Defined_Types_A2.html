🕳 a record is not the sum of its fields ↓

🕳 A record is not the sum of its fields

Put a CHAR, then an INTEGER, then a CHAR in a record and ask how big it is. You expect 1 + 4 + 1 = 6 bytes. On most machines you get 12.

The processor fetches a 4-byte integer fastest when its address is a multiple of 4, so the compiler quietly inserts padding to line each field up. Reorder the same three fields — integer first — and the record shrinks to 8.

Same fields, same data, different size, purely because of the order you typed them in. Nothing on your syllabus asks this. It is the reason real systems programmers order struct fields largest-first.

🕳 a comment is a wish; a type is a rule ↓

🕳 A comment is a wish; a type is a rule

// status must be 0, 1 or 2 DECLARE Status : INTEGER

That comment is doing a job the type should be doing. It is a note to a human, and humans are exactly the part of the system that forgets. Nothing stops Status ← 7.

Whenever you catch yourself writing a comment that restricts a value, you have found a type that wants to exist. Professionals call this making illegal states unrepresentable — and it is the same instinct as this lesson, one floor up.

Real pointer arithmetic is a C course. The famous one is Carnegie Mellon's 15-213 / 18-213, Introduction to Computer Systems — one course, cross-listed between their computer science and engineering schools, and widely held to be among the best undergraduate courses anywhere. Its Bomb Lab hands you a compiled binary with no source code and asks you to defuse it by reading the disassembly. If that sentence made you sit up, come and find me.
🕳 the billion-dollar mistake · why 64-bit is faster ↓

🕳 The billion-dollar mistake

If a pointer holds an address, what does it hold before you have given it one? In 1965, designing ALGOL W, Tony Hoare added the null reference — a pointer pointing at nothing — "simply because it was so easy to implement."

In 2009 he stood up at a conference and called it his billion-dollar mistake: forty years of crashes, vulnerabilities and repairs, from one convenient shortcut.

You will meet it within a fortnight. When a linked list is empty, its first pointer has to point at nothing — and every operation you write has to survive that.
So where does it actually point? At 0x0000000000000000 — address zero, all bits off. And that is not an accident of laziness: the operating system deliberately leaves the lowest page of memory unmapped, so following a null pointer touches an address that belongs to nobody and the hardware traps instantly. The crash is engineered. A null dereference is loud and immediate precisely so that it cannot be quiet and gradual — a wrong answer you find in one second instead of one year.
(Strictly, C only promises that writing 0 in your source produces a null pointer — a few historical machines used a different bit pattern. On everything you will ever touch, it is zero.)

🕳 Why is a 64-bit machine faster?

Not because 64 is bigger than 32. The honest answer is three things, and the first one is exactly the instinct this slide just gave you.

1 · Twice as many registers. 32-bit x86 gave the compiler 8 general-purpose registers; x86-64 gives 16. When registers run out the compiler spills a variable to memory and loads it back later — and every spill is a trip out to RAM. More registers, fewer trips. That is your intuition, and it is the real mechanism — the win is not "wider", it is less going to memory.
2 · More than 4 GB. 32 bits of address is 4 GiB, and a game that wants more must stream and re-stream. 3 · Arguments travel in registers in the 64-bit calling convention instead of being pushed on the stack. Again: fewer memory references.
And the part nobody mentions: it also costs you. Every pointer doubles from 4 bytes to 8. A structure full of pointers gets bigger, so fewer of them fit in cache, so you go to memory more often. 64-bit is a trade, not a free upgrade — which is why an ABI once existed to give you the 16 registers while keeping 32-bit pointers.
🧾 YOU CAN FEEL THIS ONE — HOLLOW KNIGHT
The early builds and the later ones do not respond the same way. The input latency — the gap between your thumb and the nail — got measurably shorter, and players noticed before anyone explained why. The 64-bit build is what did it, and Team Cherry wrote it up rather than leaving players to guess.
That last part is the bit worth keeping. Other things changed in those releases too, so "it got faster when X changed" is never by itself the same claim as "X made it faster" — the two only become the same claim when somebody measures and says so. Here, somebody did.

🕳 what a set is underneath ↓

🕳 What a set is underneath — the hash table

Almost every real set is a hash table. Take an array of, say, 16 slots. Run the element through a hash function that turns it into a number, take that number MOD 16, and that is the slot it lives in.

"Chen" → hash → 90514 → MOD 16 → slot 2 "Dara" → hash → 41127 → MOD 16 → slot 7

So "is this in the set?" is one calculation and one look, whatever the size. Not a search. A calculated address.

Two things land in the same slot? That is a collision, it is completely normal, and the table just keeps a little list there. A good hash function does not avoid collisions — it spreads them evenly.
And now the set's two rules are one rule.
Order is gone because the slot is decided by the hash, not by you.
Duplicates are impossible because the same value hashes to the same slot every time, so the second copy arrives where the first one already is.
Those are not two facts about sets. They are one fact about hashing.
📐 SAME WORD, COMPLETELY DIFFERENT JOB
You will meet hashing again in security, and it will look like the same idea. It is not.
This hash wants to be fast and to spread things out; collisions are fine and reversing it is nobody's concern.
A cryptographic hash wants to be impossible to run backwards, and a single collision that anyone can find is treated as the death of the algorithm.
One shares out. One locks up. Do not let the shared word talk you into thinking they are relatives.

You will build one of these yourself later in the year — twice. Once when a dictionary needs somewhere to live, and once when a file needs to find one record among two hundred thousand without reading them all.

How it is marked — and the five ways it is lost

itemmksthe halves
enumerated2TYPE X = · (values)
pointer2TYPE X = ^ · the target type
record4TYPE+ENDTYPE · DECLARE on every field · fields right
set4TYPE X = SET OF … · DEFINE Y (…) : X
a variable1DECLARE V : X
Every declaration is marked in halves. So write the half you know. A blank line scores nothing; half a line scores half.
1 · Quoting an enumerated value. ← "C350" is wrong. It is not a string.
2 · Declaring the field as STRING when part (a) just made you a type for it. The most expensive mistake on the question.
3 · A set with no DEFINE — half the marks left on the table.
4 · Forgetting a pointer may point at your own type — ^Parts, not just ^INTEGER.
5 · Assuming enumerated values look like words. TYPE Prime = (2, 3, 5, 7, 11) is a real mark scheme. They are still names.
