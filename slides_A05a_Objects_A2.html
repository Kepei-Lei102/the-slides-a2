P3 + P4

The record you already have — and the one thing it cannot do

// from A1 — a record TYPE Student DECLARE Name : STRING DECLARE Grade : INTEGER ENDTYPE
It knows what a student is.
Ask it to promote a student and it has nothing to say — the verb has to live somewhere else, in some procedure, next to every other procedure in the file.
// A5 — the same fields, plus the verbs CLASS Student PRIVATE Name : STRING PRIVATE Grade : INTEGER PUBLIC PROCEDURE Promote() Grade ← Grade + 1 ENDPROCEDURE ENDCLASS
A class is a record that owns its verbs.
And this is not a teaching device — it is Cambridge's own convention, printed on the Paper 4s: "A class declaration can be used to declare a record. If the programming language used does not support record formats, a class can be used." The board treats the two as interchangeable, which is exactly the claim above.

P3

…and the third spelling, which is the one they mark

Same class. Paper 3 wants it in pseudocode, and this dialect is new to you.

CLASS Pet PRIVATE Name : STRING PRIVATE Age : INTEGER PUBLIC PROCEDURE NEW(GivenName : STRING, GivenAge : INTEGER) Name ← GivenName Age ← GivenAge ENDPROCEDURE PUBLIC FUNCTION GetAge() RETURNS INTEGER RETURN Age ENDFUNCTION ENDCLASS MyPet ← NEW Pet("Tom", 3) OUTPUT MyPet.GetAge()
Four things you have never written. CLASS … ENDCLASS · PRIVATE / PUBLIC on attributes and methods · the constructor is a procedure called NEW · an object is made with ← NEW ClassName(…).
Python syntax on a Paper 3 answer is the single most expensive habit in this unit.
P3

🎮 Why private? — the invariant we want to preserve

Two bank accounts, same class, one difference. Left: the balance is public — write to it directly. Right: the model uses a hidden balance, and sanctioned writes use a setter with one IF in it.

Concept model: all sanctioned writes use the setter. Python __name is name mangling, not a security boundary.

P3

What that actually bought you

The rule has one home. With a public attribute, every place in the program that writes a balance has to remember the rule. With a setter, the rule lives in one method — and a rule in one place is a rule you can change, test, and trust.
The object can no longer be wrong. That is a stronger claim than "the data is hidden": it means no sequence of legal calls, by anyone, can put it in a state its own rules forbid.
And it is the published definition.
"Encapsulation — putting properties and methods inside a class // ensures sensitive data is hidden from users by hiding values of a structured data object inside a class." — Nov 2022 P32, published
So `public` is answered too. It is not decoration — it is the decision about who is allowed to touch this. Two words down, one to go.
P3 + P4

Getters and setters — not boilerplate

PUBLIC FUNCTION GetBalance() RETURNS INTEGER RETURN Balance ENDFUNCTION PUBLIC PROCEDURE SetBalance(New : INTEGER) IF New >= 0 THEN Balance ← New ENDIF ENDPROCEDURE
Getter — method that is used to return the value of a property.
Setter — method that is used to update the value of a property.
Both published, Nov 2022 P32. One clause each — a paragraph about good practice earns exactly the same one mark.
The setter guards writing. The getter guards reading. A getter is a place where "who is asking?" can live — return the balance only to the account holder, hand back ****1234 instead of the card number, write a line in the audit log every time somebody looks. A public attribute cannot ask any of those questions. It is a standing promise that anyone may read it, in full, and that nobody will ever know they did.
And a getter need not return a stored value at all. GetFahrenheit() on a class that stores Celsius does the sum and hands it back — the caller cannot tell, and does not need to.
P4

One copy of the code, many copies of the data

Three pets exist. How many copies of birthday() are there in memory?

attributes — one set PER OBJECT
Tom's age is not Jerry's age. Three objects, three ages, and changing one changes nothing else.
methods — ONE set, shared
There is exactly one birthday(). Every object runs the same code; the only thing that differs is which object it was called on.
You have seen this before. In A3b, a hundred recursive calls shared one copy of the function and each got its own stack frame. Same architecture, different name: the code is shared, the data is not.
P4

Instance state and a class counter

The real difference is WHEN the memory exists.
Not class-level — the field has no memory anywhere until new runs. Then each object is given its own slot. Three pets, three name slots, and not one of them existed a moment earlier.
Static — the field is given its address the moment the class is loaded, before any object exists, and there is exactly one copy of it for the whole run.
Which is why main is class-level. The program has to start somewhere, and at that instant nothing has been instantiated — so the only storage that exists is the class's own. A non-class-level main would have nowhere to live.

Turning a problem into classes

A syllabus bullet in its own right: "understanding of how to solve a problem by designing appropriate classes."

A library lends books. Each book has a title, an author and a status — on the shelf or out on loan. A member has a name and a membership number, and may borrow up to six books at a time.
in the descriptionbecomeshere
nounsclassesBook · Member
adjectives / facts about a thingattributesTitle, Author, OnLoan · Name, Number
verbsmethodsBorrow(), Return()
The heuristic is not a law and it is worth saying so. "Up to six books" is a noun phrase that is not a class — it is a rule, and rules live in methods, usually in the setter that would break them. Where the nouns run out is where judgement starts.

Check the mechanism

Ada has 7, Max has 0. self names the receiver. Typical mistake: one class-level score shared by every player.
Optional full reference
GetScore returns self.__score. ada.GetScore() → 7; max.GetScore() → 0. The methods are defined on the class; each instance stores its own values. __score uses name mangling, not enforced security.
