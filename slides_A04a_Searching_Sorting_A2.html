P3 + P4

Linear search — the one you would have invented

Start at the beginning. Look at each item. Stop when you find it, or when you run out.

Its whole case is what it does not need. No order. No preparation. No promises. Hand it any array at all and it works — and for one search of unsorted data it is exactly the right tool. Best case 1 look; worst case n; on average about n ÷ 2.
P3 + P4

Binary search — you have done this since you were six

"I'm thinking of a number between 1 and 100." Nobody guesses 1, then 2, then 3. Everybody guesses 50 — and every answer throws half the numbers away. Worst case: 7 guesses. Because 2⁶ = 64 is not enough and 2⁷ = 128 is.
int Low = 0, High = A.length - 1; while (Low <= High) { int Mid = (Low + High) / 2; if (A[Mid] == Target) return Mid; if (A[Mid] < Target) Low = Mid + 1; else High = Mid - 1; } return -1;
The three ways to get it wrong, and every one of them appears in real scripts:
① while (Low < High) — misses an array of one, so it never finds the last candidate.
② Low = Mid instead of Mid + 1 — the window stops shrinking and it loops for ever.
③ forgetting that it returns −1 when the window collapses. That collapse IS the answer "not there".
And one line the exam wants said out loud: the array must already be sorted.

📐 The precondition is the trade

Binary search does not have speed. It rents it, and the rent is sorted data. So the real question is never "which search is faster?" — it is what are you actually doing?

Searching once? Do not sort. The sort costs a thousand times what the single scan you are avoiding would have cost.
Searching again and again? Sort once, then binary-search for ever. With today's sorts that investment pays for itself after about 1 020 searches.

Insertion sort — sort a hand of cards

§19.1's other named sort, and the one you have not written yet. You already know how to do it: you do it every time you pick up a hand of cards.

Green is the sorted hand. Amber is the card being carried back into it.

Four moves, said before any code:
① pick up the next card
② while the card on its left is bigger, slide that card one place right
③ drop yours into the gap
④ repeat, from the second card to the last
Why start at the second card? One card on its own is already a sorted hand.
The invariant: everything to the left of the card you are holding is always sorted. Each drop keeps it true, so when the last card is dropped the whole array is sorted. That is the proof it works.

Why is the drop Y + 1? The walk stops on the first card that is not bigger, or at −1. The gap is one place to its right.
Check Y ≥ 0 before indexing. Python evaluates and left to right and stops when the guard is false. Python’s negative indices mean an incorrectly ordered condition can read the last item without raising an exception. Guard first expresses the valid sorted-prefix range.

The same four moves in pseudocode — arrays start at 1

FOR X ← 2 TO n // ④ from the second card CurrentValue ← DataArray[X] // ① pick it up Y ← X - 1 WHILE Y >= 1 AND DataArray[Y] > CurrentValue DataArray[Y + 1] ← DataArray[Y] // ② slide it right Y ← Y - 1 ENDWHILE DataArray[Y + 1] ← CurrentValue // ③ drop into the gap NEXT X

Only the edges move: 2 instead of 1, >= 1 instead of >= 0. The moves are the same.

What Paper 3 schemes award, one mark each: an outer loop starting at the second item · the value stored before the walk · a WHILE that compares, with the right exit · data moved to the next element · the counter going down · the value re-inserted outside the inner loop.
Two arrays that belong together (an ID and a name, a score and a student)? Every move happens to both: two values picked up, two slides, two drops. Sort one without the other and every name ends up next to someone else's ID.
The classic lost mark: the drop written inside the WHILE. Then the card is dropped after every slide instead of once, at the end of the walk.

P4

🕳 A sort is a shape, not something you do to numbers

Nov 2024 Paper 41 asks for a bubble sort in ascending alphabetical order, using a supplied function CompareStrings(). © UCLES

// numbers if (A[j] > A[j+1]) swap; // names — the SAME algorithm if (CompareStrings(A[j], A[j+1])) swap;
Two loops, a comparison, a swap. Only the comparison changed, and it changed into a function call. The sort did not need to know what it was sorting.
That is why it is worth learning four of these. An algorithm is a shape you can pour different things into — dates, names, scores, records ordered by one field.
Python offers an ordering key. For example, sorted(records, key=lambda row: row["score"]) orders records by one field. In the supplied exam algorithm, use its comparison function and its documented return meaning. The traversal shape stays the same when the comparison changes.
off-syllabus

Selection sort — the third strategy

Find the smallest thing left. Swap it into place. Once per pass, and never again.

🧾 THIS ONE IS NOT ON YOUR SYLLABUS
9618 §19.1 names two sorts — insertion and bubble — and "selection sort" appears in none of the last five years of papers. It is here because bubble exchanges, insertion inserts, and this one selects: three different strategies is what makes the word judge mean anything. And because it is the only sort in this room that nobody can have memorised.
The whole description, and you get no code: walk the unsorted part, remember where the smallest value is, and when you reach the end, swap it with the first unsorted slot. Repeat.
It has a fingerprint. One swap per pass means at most n − 1 swaps, ever — where bubble on the same 40 items averages 364. Remember that; the boss checks it.
