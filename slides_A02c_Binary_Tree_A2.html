The two structures you own have opposite weaknesses

find a value insert a value

Halving needs to jump to the middle; cheap insertion needs nothing to move. One structure per column — and somebody is going to ask for both at once.

The binary tree refuses to choose.
Halving to find, two writes to insert — and the price appears at the end of the lesson.

P3 + P4

Give the node a second pointer

One field more than the linked list's node. Written the way you would actually write it — names, not column numbers.

class Node: def __init__(self, data): self.left = None # the smaller side self.data = data self.right = None # the larger side
class Node { Node left; // the smaller side int data; Node right; // the larger side }
Three fields, two of them pointing at more nodes. That is the whole new idea — the linked list's node with one extra arrow, and the arrows now have directions that mean something: smaller to the left, larger to the right.
what you would writewhat the exam writes
node.leftArrayNodes[n, 0]
node.dataArrayNodes[n, 1]
node.rightArrayNodes[n, 2]
The exam's array is this record with the names filed off. Same object, worse handwriting — a row is a node, a "pointer" is a row number, and the field names become 0, 1, 2. Learn the shape here; type the columns in the exam.
🧾 And Cambridge writes it both ways. Nov 2024 Paper 31 asks about BinTree[NowPtr].LeftPtr — named fields, on a real paper — while every Paper 4 tree question uses the numbered columns. Two costumes, one structure.
P3 + P4

The same node, as the exam stores it

DECLARE ArrayNodes : ARRAY[0:19, 0:2] OF INTEGER // [n, 0] LeftPointer — index of the smaller side // [n, 1] Data // [n, 2] RightPointer — index of the larger side DECLARE RootPointer : INTEGER // -1 = empty tree DECLARE FreeNode : INTEGER // next unused row

Cambridge's own declaration, from Nov 2022 Paper 41. The names vary by paper — RootPtr, FirstNode, FreePtr — the shape never does.

Same trick as the linked list, one column wider: a row of the array is a node, a "pointer" is an index, and −1 is the value that cannot be one. Empty tree? RootPointer = −1. No child? −1. Fourth time this unit — say it before the slide does.
📐 WHERE DID THE FREE LIST GO?
The linked list threaded its spare nodes into a second chain, because deleting handed nodes back. The exam's tree never deletes — the syllabus asks for delete on stacks, queues and linked lists only — so nothing is ever handed back, and FreeNode collapses into a plain counter: the next unused row, plus one after every insert. Simpler on purpose, and the papers say so out loud: "nodes cannot be deleted from this tree."
P3 + P4

One rule makes it work — at every node

Smaller → left. Larger → right.
Not just at the root — at every node, all the way down. The rule is not a property the tree has; the rule is the tree. Break it at one node and the structure is just circles and arrows.

And equal?
Cambridge's own pseudocode tests IF NodeData < Data and sends everything else right — so equal goes right. A convention, not a law; state it and follow it, because the marker follows the paper's.

Read the rule again and notice what it buys: standing at any node, one comparison tells you which half of everything below to abandon. That is binary search, built into the furniture.

P3 + P4

Finding is halving — built into the shape

Binary search from AS needed a sorted array and index arithmetic. Here the comparisons ARE the structure.

Every comparison discards an entire subtree. A million values, about twenty questions — the AS binary-search promise, kept by furniture instead of arithmetic. And "return −1 when it is not there" is the sentinel again, working its fifth job of the unit.
🕳 unless the tree was built wrong ↓

🕳 The tree that is secretly a list

Insert 1, 2, 3, 4, 5, 6, 7 — in order — and look at what the rule builds.

Index Left Data Right 0 -1 1 1 1 -1 2 2 2 -1 3 3 3 -1 4 4 4 -1 5 5 5 -1 6 6 6 -1 7 -1

Every left pointer −1. Every node hangs right. Height 7, for 7 nodes.

Each value was larger than everything before it, so the rule sent every one right — and built a linked list wearing a tree costume. Searching it asks every node in turn: O(n), the exact thing the tree existed to escape.
The tree's advantage depends on the order the data arrived in. You met this exact sentence at AS: insertion sort is fast on nearly-sorted data and slow on reversed data — same lesson, one structure later. Random order → roughly balanced → halving. Sorted order → a stick.
🧾 OUTSIDE THE EXAM HALL Real systems cannot choose their arrival order, so real trees rebalance themselves as they grow — the AVL and red-black trees inside every database index and every TreeMap. The problem on this slide is why they exist. 9618 never asks about them — it asks you to know the problem, which you now do.
P3 + P4

Walk it in order — and the data comes out sorted

Left side first, then the node, then the right side — at every node. Three lines.

Look at line 4. InOrder calls InOrder. The function uses itself, twice, and the machine does not object. Nobody has explained why that is allowed — and this deck is not going to. Two lessons.
🧾 Three orders exist and the exam uses them: in-order (left · node · right — sorted output), pre-order (node first), post-order (node last — asked on Nov 2022 Paper 41). Same three lines; only the print moves.
P3 + P4

The dictionary — ADTs built from ADTs

A key → value store: look up by name, not by position. "Amir" → 71. The syllabus verb is exact: describe it, and demonstrate how it can be implemented from built-in types or other ADTs — two parallel arrays and a linear search of the keys is a complete, honest answer.
FUNCTION Lookup(Key : STRING) RETURNS INTEGER FOR i ← 0 TO Count - 1 IF Keys[i] = Key THEN RETURN Values[i] ENDIF NEXT i RETURN -1 ENDFUNCTION
And the fast version is the hash idea — feed the key to a function that computes where it lives, and the search disappears: one calculation instead of a walk. That is the machinery behind Python's dict and Java's HashMap — both of which are banned in this unit's homework, because using a dictionary to build a dictionary answers a different question.
🧾 HOW OFTEN THIS IS ASKED Across every released Paper 3 and Paper 4 from 2021 to 2025, the dictionary has never yet been examined. It is on the syllabus, so it is fair game — and a first appearance lands exactly on the cohort that skipped it.
P3

The graph — key features only, by decree

Nodes, and the connections between them — where the connections matter more than any order. Directed or not (one-way streets vs handshakes), weighted or not (does each edge carry a cost?). A tree is a graph with rules; a graph is what is left when you delete the rules.
What it is for: anything that is genuinely a network — roads, friendships, flight routes, the web's links, your class timetable's clash constraints. The exam's verb is justify its use for a given situation: name the entities as nodes, the relationships as edges, and say why order alone cannot carry the information.
📐 THE SYLLABUS'S OWN CARVE-OUT
Its exact sentence: "Candidates will not be required to write code for a graph structure." The only structure in the unit with a no-code guarantee — so revision time goes to features and justification, not implementation.
And the payoff is queued: at the end of the year a graph gets searched — shortest routes, A-star, the algorithms inside every map app. The structure arrives now; the verbs arrive then.
🧾 HOW OFTEN THIS IS ASKED Like the dictionary: never yet, in five years of released papers. On the syllabus, so know the features and the justify-sentence — that is the whole ask.
P3 + P4

The whole family — one sentence each

"Justify its use for a given situation" is the examined verb, and a justification is one sentence naming the property that fits.

structurestrong atweak atthe justification sentence
stacklast-in-first-out, O(1) both ends of one endreaching anything below the top"the most recent item must be dealt with first" — undo, back button, calls
queuefirst-in-first-out, fairnessreaching the middle"items must be handled in arrival order" — printers, buffers, schedulers
linked listinsert/delete anywhere, two writesno index — finding is O(n)"the data changes constantly and never needs jumping into"
binary treefind AND insert in O(log n), sorted for freearrival order can degrade it to O(n)"the data must stay searchable while it grows"
dictionarylookup by key, not positionno order at all"items are found by name, never by position"
graphrelationships between itemsno order, no hierarchy, code not asked"the connections carry the information" — routes, networks
Every row is the same move: name the property, match it to the scenario. A justification that does not name a property — "a tree is more efficient" — scores nothing on any paper.
